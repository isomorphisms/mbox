# Executable filing hardening

The deterministic corpus generator is `corpus.py`: 49 mailbox cases, independent
entry bytes, header blocks, expected selections and length-derived byte ranges.
No parser generates its own expectations. `test_filing.py` also checks the original
shared corpus and manifest hashes. The exact fallback reference executor is
`examples/autogenerated/safe-filing/{framing,spec_list,filing}.py`.

This is Python reference execution, not qualification of Idriç or D. The preferred
Idriç executor remains a separate implementation and must consume this corpus.
The preserved attempt explains the unavailable runtime and required durable I/O.

## Supported bytes and policy

Every line-leading `From ` frames an mboxo occurrence, regardless of date validity.
Read/copy never normalize LF/CRLF, decode RFC bytes, strip envelopes, unescape
`>From `, or regenerate headers. A raw copy of an existing occurrence requires no
new escaping: unescaped `From ` already framed an occurrence in the source.
Malformed headers are preserved; they cannot lend a continuation to the previous
valid field. An EOF envelope without LF is retained as a headerless occurrence.
Nonempty preambles, headers over 4 MiB, and envelopes over 4096 octets are refused.

SPEC-LIST is an ASCII case-insensitive **substring** in exactly From, Sender,
Reply-To, To, Cc, Subject. A longer string containing that substring matches under
the established policy; `SPEC LIST`, `SPEC_LIST`, and incomplete markers do not.
Body text, List-ID, Delivered-To and arbitrary X fields do not select mail.
Repeated headers and repeated/missing Message-ID values do not collapse occurrences.

Plans are streaming TSV. They bind exact absolute source/destination, mode, full
source/archive SHA-256 and inode/metadata fingerprints, executor and policy, every
occurrence's half-open byte range/digest/envelope/Message-ID/evidence, counts and
expected source byte/count effects. Binary evidence is base64. Ordinals are
display aids, not sole identities. No source/archive mutation occurs in planning.
Consumers require the final summary and discard output from a failed planner.

## Transaction and recovery contract

All mutation requires a marked disposable workspace under exclusive caller
ownership. The cooperative executor flock is not a mail-delivery lock. Every
source change (append, replacement inode, shrink, prefix or metadata change) is
refused; append-tail recovery in the general contract is deliberately unimplemented
in this executor. It must not silently interpret an unsupported lock as permission.

Archive publication replaces a verified prepared file containing the exact old
archive bytes followed by selected occurrences. A nonempty old archive must end
in LF and have valid supported framing; no newline is silently inserted.
The journal binds its prepared inode, digest, original baseline and plan.
Equal records already in the archive are preserved, and each selected source
occurrence is added exactly once for **this transaction**. A new copy plan is a
new requested copy, not deduplication; repeated copies under different plans can
intentionally add occurrences. Rerun the same plan/journal for recovery.

| Failure or interruption | Required surviving copies | Restart |
| --- | --- | --- |
| Before/during archive preparation; open, permission, partial write, sync, close, verification failure | Original source and old archive; partial private output may remain | Revalidate plan; rebuild that transaction's output |
| Verified archive prepared, before archive replacement | Source, old archive, verified prepared archive | Verify inode/digest then publish |
| Archive replacement succeeded before its state receipt | Source and transaction-owned new archive; old archive backup | Recognize prepared inode/digest; never append again |
| Archive verified, during source backup/rewrite/preparation/verification | Original source and verified new archive | Revalidate source and rebuild replacement |
| Before source replacement or rename failure | Source, verified archive, durable original-source backup and replacement | Validate all fingerprints before replacing |
| Source replacement succeeded, including sync/receipt failure | Verified archive, replacement source and durable full original-source backup | Recognize prepared source inode/digest; finish receipt |
| Temporary output without journal | All existing source/archive/temporary bytes | Refuse; do not delete unknown recovery copies |
| Files changed after completed receipt | All current copies | Refuse rather than silently rerun |

The source backup and journal remain after completion. Tests exercise exceptions,
23 actual fsync-call injections, and abrupt `os._exit` process termination at ten
boundaries. They do **not** emulate loss of power, torn sectors, filesystem recovery,
or SDF delivery. No power-loss crash-safety claim is made.

## Resources and mutants

Mailbox I/O uses bounded 64 KiB fragments, including `readline(size)` for huge
single lines. Full records and the full manifest are never collected. Header
state is bounded by the 4 MiB limit; memory is O(header limit + I/O chunk),
independent of body length and message count. Plans and transaction copies use
disk space proportional to input/output, including a full original-source backup.
The normal suite runs a 128 MiB single body line and 100,000 selected small messages;
its receipt records measured peak Python allocations and elapsed time, not a
machine-independent performance promise.

`mutations.py` edits actual executors and runs named behavioral regressions. It
requires a real unittest failure; syntax failures are rejected as mutant construction
errors. Thirteen variants cover body matches, missing header, wrong archive entry,
missing envelope, merged/split records, deletion before verification, stale rewrite,
lost keeper, duplicate selection, wrong spool, aliasing and partial-write success.

Run the normal suite with Python 3.9+ via `tests/hardening/test_filing.py`, then
`tests/hardening/mutations.py`. Python 3.9 syntax is checked here; local execution
version and host-specific NOT_RUN boundaries are recorded in evidence. CI adds
actual Python 3.9/3.12 execution. The `MBOX_QUICK` flag only skips resource work in
targeted developer/mutation runs; Kitchen qualification removes it.
